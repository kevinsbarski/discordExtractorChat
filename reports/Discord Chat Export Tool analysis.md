# Dissecting a Discord exporter, and rebuilding it

The "Discord Chat Export Tool" (Chrome Web Store ID `lmoceiadfbnpofjbmgemloenlfkhhbhl`, v1.7.0) is a Plasmo-built Manifest V3 extension that exports one open Discord conversation over a chosen date range by **automating the signed-in user's account against Discord's private web API**. It gets authentication not by asking the user, but by silently copying Discord's own `authorization` header off the page — the same user-token-capture technique that malware and self-bots use, and a direct violation of Discord's Terms, Developer Policy, and Community Guidelines that has gotten comparable tools' users logged out, password-reset, and penalized through 2026 ([Discord ToS](https://discord.com/terms); [DCE issue #1497](https://github.com/Tyrrrz/DiscordChatExporter/issues/1497)). It converts the two picked dates to snowflakes, runs one message-search call to find an anchor, then pages `GET /channels/{id}/messages?limit=50` backward, filtering by timestamp client-side. Output is HTML (React `renderToStaticMarkup` into a hand-written template), CSV, or XLSX (SheetJS); attachments are a **separate, manual** download step that writes files straight into a user-picked folder and are never bundled with the transcript. It is free up to **100 messages per run** (200 after a one-click "rate us 5 stars" prompt), with unlimited use behind a **$9.99/mo (up to $84.99/yr)** Paddle subscription gated only client-side. Building an equivalent is cheap — roughly the one-time **$5** Chrome Web Store fee, all-open-source libraries, no server and **no LLM required** — but any faithful rebuild inherits the same account-ban risk, so the only low-risk paths are Discord's official data package or a bot token. The user's three screenshots were unavailable to the researchers, so every UI detail below was reconstructed from the v1.7.0 bundle source and the store listing; this is flagged throughout.

## Feature set is deliberately thin: one conversation, a date range, three formats

The product does exactly one thing per run: export the single channel, DM, group DM, or thread currently open in the active Discord tab, over a start/end date range. The **popup** (reconstructed from `popup.100f6462.js`, since the screenshots were not available) is a 420px-wide panel with Home/Upgrade/Profile tabs. Home shows a channel card, two HeroUI date pickers — "Start Date" defaulting to four years ago and "End date" to today, both day-granularity, US-locale, **browser-local time zone, with no presets** — and a "Start Exporting" button; that is the entire control surface ([store listing](https://chromewebstore.google.com/detail/lmoceiadfbnpofjbmgemloenlfkhhbhl?hl=en)). There are no toggles for including or excluding attachments, images, embeds, avatars, or reactions, no filename field, no multi-channel or whole-server selection, no output splitting, and no language selector — the researchers searched for all of these in the developer modules and found them absent. All in-app copy is hard-coded English despite 55 declared locales; only the extension name is actually localized.

Clicking Start opens a dedicated **Export tab** (`chrome-extension://…/tabs/Export.html`) that does all the real work: an auto-starting fetch with a progress bar and Pause/Continue, "Messages" and "Attachments" counters, a split "Download Messages" button whose menu offers HTML/CSV/XLSX, a separate "Attachments" dialog, and a 10-row preview. The store's own screenshot-2 (described in the notes, image not seen by researchers) shows a completed run of **1,884 messages and 186 attachments** — a figure the free tier cannot reach, underscoring that the headline "export all messages with a single click" is a paid capability. The listing markets exactly three features: export all messages from any channel, export private conversations, and export attachments (images, videos, audio, documents) ([store listing](https://chromewebstore.google.com/detail/lmoceiadfbnpofjbmgemloenlfkhhbhl?hl=en)). Supported conversation types are guild text channels, threads and forum posts (each post is a thread), DMs and group DMs; forum/media *parent* channels (API `type` 15/16) are refused with a prompt to open a specific post. Notable product tells of a shared developer template: the Upgrade screen's feature table still advertises **"Delete Tweets / Delete Replies"** — leftover copy from an unrelated Twitter tool — and a cross-promotion dropdown is labeled "ACME features".

## Fetching rides the logged-in session; authentication is silent token capture

The extension never asks for credentials. A **MAIN-world script** that the service worker registers at runtime on `https://discord.com/*` at `document_start` wraps `XMLHttpRequest.prototype.setRequestHeader`, watches for Discord's own `authorization` header, and writes that value — the user-account token — into a `data-token` attribute on the page `<body>`. An isolated content script reads that attribute back and hands it, with the channel/guild IDs parsed from `window.location.href`, to the popup via `chrome.tabs.sendMessage`; the popup then passes everything — **including the raw token — in the query string of the Export tab's URL**, and the Export page sends it verbatim as the `authorization` header (no `Bearer`/`Bot` prefix) on every API call ([v1.7.0 `injected.a4186a2d.js`](file:///Users/kevinsbarski/Library/Application%20Support/Google/Chrome/Default/Extensions/lmoceiadfbnpofjbmgemloenlfkhhbhl/1.7.0_0/injected.a4186a2d.js)). The static analysis confirms the token is **never written to `chrome.storage` and never sent to any non-Discord host**; but it does sit exposed as a DOM attribute readable by any script on the page and in the extension-tab URL (address bar, session restore, any extension with the `tabs` permission). This is the structural weakness worth fixing in any rebuild: it is functionally the capture method used by token-grabber malware ([K7 Labs](https://labs.k7computing.com/index.php/the-discord-token-grab/)), and Discord's own auth model treats possession of that token as full account access, unprotected by login-time MFA.

All message traffic hits Discord's web API at `https://discord.com/api/v9` (the version the web client uses) with only `accept`, `accept-language`, and `authorization` headers — conspicuously **without** the official client's `X-Super-Properties` fingerprint, which anti-abuse systems weight heavily, making this traffic easy to distinguish from a real client ([docs.discord.food](https://docs.discord.food/reference#client-properties)). The date-range mechanism is a hybrid of server search plus client filtering, matching how Discrub and DiscordChatExporter (DCE) work:

| Step | Call | Purpose |
|---|---|---|
| Dates → snowflakes | `(ms − 1420070400000) << 22` (BigInt) | Discord-documented pagination bound ([Snowflakes](https://discord.com/developers/docs/reference#snowflakes)) |
| Find anchor | `GET /guilds/{id}/messages/search` (`min_id`,`max_id`,`channel_id`,`include_nsfw`), or `/channels/{id}/messages/search` for DMs | One call to locate the newest in-range message (default sort is newest-first) |
| Page backward | `GET /channels/{id}/messages?limit=50` with `around=<anchor>`, then `before=<oldest id of previous page>` | The real paging loop |
| Filter | decode each snowflake to ms, keep if `start ≤ t ≤ end` | Client-side range enforcement |
| Metadata | `GET /channels/{id}`, `GET /guilds/{id}` | Title, icon, forum detection |

Paging runs strictly newest-to-oldest and **stops at the first page with zero in-range messages** ([Discord Get Channel Messages docs](https://discord.com/developers/docs/resources/message#get-channel-messages)). Because `before`/`after`/`around` are mutually exclusive and messages always return newest-first, this one-cursor-plus-filter design is the standard workaround. Two correctness gaps follow from the code: an HTTP 202 "index not yet available" from search is treated as success (so an unindexed channel reports "no messages"), and messages newer than the anchor that fall outside the `around` window can be silently missed.

## Attachments download separately and are never packaged with the transcript

This is the single biggest divergence from what a user might expect, and it directly explains a recurring complaint (an HTML export whose images had vanished). The HTML, CSV, and XLSX outputs contain only **remote `cdn.discordapp.com` URLs**, not embedded media; the sole inlined image is a base64 default-avatar fallback. Downloading the actual files is a distinct, manual action in a "Download Attachments" dialog: the user filters by category (Photos/Videos/Audios/Others), ticks files, picks a folder via `window.showDirectoryPicker({mode:"readwrite"})`, and the page fetches each selected file one at a time and writes it with `createWritable()`. Only *message* attachments (plus those inside the first forwarded snapshot) are covered — avatars, emoji, stickers, and embed images are never downloaded. The loop has **no concurrency, no retry, no HTTP-status check, no size cap, and no signed-URL refresh**; because status is never checked, an expired or 403 URL is saved as the "file" and still counted as a success, so the final "All files downloaded successfully!" toast can be false. The folder is flat, files keep Discord's original names, and collisions get " (n)" suffixes.

This matters because Discord attachment URLs are **signed and expiring** — carrying `ex` (expiry), `is` (issued), and `hm` (signature) parameters, reportedly valid ~24 hours — and the documented refresh path (re-fetching the message, or the undocumented `POST /attachments/refresh-urls`) is **never used** (`refresh-urls` and `media.discordapp.net` appear zero times in the bundles) ([Signed Attachment CDN URLs](https://discord.com/developers/docs/reference#signed-attachment-cdn-urls); [BleepingComputer, Nov 2023](https://www.bleepingcomputer.com/news/security/discord-will-switch-to-temporary-file-links-to-block-malware-delivery)). So a saved HTML file is styled offline but its media is fetched live from Discord's CDN and dies when links expire or a server is deleted. **Nothing is ever zipped**; message files save via a temporary `<a download>` on a `blob:` URL (which is why no `downloads` permission is needed), named `chatlogs-<serverId>-<channelId>` or `chatlogs-@me-<channelId>`. On export formats: HTML is assembled by running each message through React `renderToStaticMarkup` and wrapping the result in a string template that inlines the whole ~230 KB compiled Tailwind/HeroUI stylesheet and emits **no JavaScript** — so despite its menu label ("Searchable page with filter, paging and links") it has no search, filter, or paging. CSV and XLSX come from SheetJS 0.18.5 (`json_to_sheet` → one "Sheet1" workbook); a JSON writer exists in code but is not wired to any button. Reactions are never read at all (the string "reactions" appears zero times in the Export bundle), and embeds keep only a subset of fields (no `image`/`video`/`url`, and `fields` are captured but not rendered).

## Limits, caps, and a standing terms-of-service problem

The hard product cap is the free-tier **100 messages per run**, raised to **200** the moment a user clicks "Unlock More Free Exports" — which fires an alert, opens the Web Store review page, and raises the local limit with **no verification that a review was left** (an incentivized-rating mechanic that itself violates Web Store policy, and which reviewers openly admit taking). The cap is enforced purely client-side by aborting the fetch loop after a page pushes the in-memory counter over the limit, so it is soft (a run can overshoot by up to 49 messages, already-fetched messages stay exportable, and reviewers report patching it to export 12K messages free). Paid status is a boolean from a third-party licensing backend (`worker-api.extbolt.com`, keyed on a Supabase/Google sign-in) cached as `isPaid` in `chrome.storage.local`; **downloads themselves are not gated** — free and paid output is byte-identical, no watermark. The only other technical ceilings are SheetJS's (a 32,767-char cell throws; a buggy range clamp would truncate an XLSX above ~1,048,575 rows) and browser memory.

On **rate limits, the extension does essentially nothing**: it reads no `X-RateLimit-*` or `Retry-After` header and ignores `retry_after` in 429 bodies. Any non-2xx becomes a generic error; the loop is sequential with a fixed **500 ms** pause between pages and **3,000 ms** after an error, giving up after **6 consecutive failures** with an alert — no backoff, no jitter. Steady throughput is therefore ~2 requests/s (~100 messages/s), and Discord's per-route limits are respected only by accident. The deeper issue is **platform rules**. Capturing the `authorization` header and automating the account squarely matches four separate prohibitions: self-bot/user-bot automation ([Self-Bots article](https://support.discord.com/hc/en-us/articles/115002192352-Automated-User-Accounts-Self-Bots); Community Guideline #14), "unauthorized software designed to modify the services" and automated scraping ([ToS](https://discord.com/terms)), modifying the Discord client ([Platform Manipulation Policy](https://discord.com/safety/platform-manipulation-policy-explainer)), and obtaining "account access or login tokens" ([Developer Policy #4](https://support-dev.discord.com/hc/en-us/articles/8563934450327-Discord-Developer-Policy)). Since roughly late February 2026, users of the comparable DCE tool report an enforcement wave: accounts blocked for "platform abuse"/spam, all devices logged out, and password resets triggered mid-export — behavior- and fingerprint-driven, not merely 429-count-driven ([DCE issue #1497](https://github.com/Tyrrrz/DiscordChatExporter/issues/1497)). Separately, the store listing's "will not collect or use your data" claim sits uneasily with sign-in sending the user's Google identity to the developer's Supabase and a bearer token to its licensing API, though **no Discord content leaves the device** in the code examined.

## How it is built, and what it does to stay fast (not much)

The stack is a **Plasmo MV3** extension with five contexts: the MAIN-world capture script; an isolated content script (token + URL IDs + metadata calls + the `getDetail` responder); the popup (gathers context and dates); `tabs/Export.html` (all bulk fetching, preview, export, attachment downloads); and a thin service worker (Google sign-in via `chrome.identity`, `openUrl`, MAIN-world registration, uninstall URL — it makes **no** Discord calls). The UI is React 18.2 + HeroUI on react-aria, Tailwind, framer-motion, `@internationalized/date`, dayjs, markdown-to-jsx, react-hot-toast, SheetJS, Supabase JS, and Plasmo's storage/messaging; Sentry is bundled in the worker but inert (no DSN), and there is no GA/Mixpanel/Amplitude/PostHog. A dedicated tab is used because `<a download>` and `showDirectoryPicker` need a DOM and a user gesture that an MV3 service worker lacks, and a tab survives the worker's idle limits during a multi-minute loop.

There is **no large-export machinery at all**. Every message lives in one in-memory React array (appended with a full-array copy each page, so work grows quadratically), HTML/CSV/XLSX are generated synchronously in one shot on the main thread (so the tab can freeze on large exports), and there are no Web Workers, no IndexedDB/OPFS buffering, no streaming writes, and no output partitioning. Pacing is the only "performance" feature: 50-message pages, the 500 ms inter-page sleep, time-based progress, and Pause/Continue via an `AbortController` plus a saved `before` cursor. Progress is not resumable across a tab close — a complaint reviewers raise explicitly. Peak memory is roughly the message array plus the full HTML string plus its Blob copy; V8's ~1 GiB string cap and ~2 GB in-memory blob cap are the real ceilings. (The `dist.ae9fd27b.js` chunk is just a lazily loaded framer-motion animation bundle for HeroUI, unrelated to exporting.)

## Cost: about five dollars and no AI

Using the tool is free for trivial exports and **$9.99/month, $24.99/quarter, or $84.99/year** (auto-renewing, Paddle as merchant of record, 7-day refund) for unlimited use ([ExtBolt live config](https://worker-api.extbolt.com/api/get-project-config?project_id=61a31dd7-8c69-4e82-b15e-8b5134cd6e49)). **Building** an equivalent is near-zero cost. Every framework and library in play is permissively licensed and free (WXT/Plasmo/CRXJS MIT; zip.js BSD-3; client-zip/fflate MIT; discord-markdown-parser Apache-2.0), **no server or hosting is needed** because everything runs locally against Discord's API, and the only mandatory expense is the Chrome Web Store's one-time registration fee, reported as **US$5** ([CWS Register](https://developer.chrome.com/docs/webstore/register)). Crucially, **no LLM or paid API is required** for any core feature — fetching, markdown rendering, zipping, and saving are all free local operations, and none of the reference tools (DCE, Discrub) use AI. The "LLM-ready" exports seen in some small repos are just plain text/JSONL formats. Money only enters if you choose to monetize (e.g. ExtensionPay's 5% + Stripe's 2.9% + 30¢, which makes very low prices inefficient) or add an optional cloud "AI summary," which would push message content off-device and trigger new data-handling disclosures.

## Recreating it: architecture and build steps

A clean rebuild should keep the analyzed tool's working skeleton but fix its weak points. Prior art converges on the same algorithm, so **port the approach, not the code**: DCE (MIT C#, the reference design) and Discrub Classic (MIT, the reference *browser-extension* design — React, streaming ZIP via conflux/StreamSaver, media dedupe) are both reusable with attribution, though DCE's Razor templates and unlicensed "gg sans" fonts don't transfer and its README adds a political "Terms of use" clause ([DCE repo](https://github.com/Tyrrrz/DiscordChatExporter); [Discrub Classic repo](https://github.com/pratherbytecraft/discrub-ext)). Recommended tooling in 2026 is **WXT** (very active, declarative MAIN-world scripts, built-in ZIP/publish); Plasmo — what the analyzed extension uses — has had no main-branch commits since May 2025 and should be avoided for new work.

Target architecture (empty project):
- **MAIN-world script** (`document_start`, `https://discord.com/*`) observes the `authorization` header on Discord's own requests and hands it to an isolated bridge via `postMessage` with a `event.source === window` check — **never via a DOM attribute** (the analyzed tool's weak point). Offer a manual token-paste fallback. Carry a DCE-style ToS warning.
- **Bridge → service worker** stores the token in **`chrome.storage.session`** (in-memory, not persisted), never in the URL or `local`.
- **Action click opens `export.html`**; the tab does all work: date→snowflake conversion, an omega-bounded paging loop (`limit=100`), and attachment downloads with small concurrency (2–4).
- **Fetching:** page one request at a time; **honor `X-RateLimit-Remaining`/`Reset-After` and `retry_after`**, back off exponentially on repeated 429s, stop on 401/403 (each counts toward the 10,000-per-10-min invalid-request ban). Handle 202 "index not yet available" by retrying after `retry_after`.
- **Content handling:** render through a Discord markdown AST (`discord-markdown-parser`), resolve mentions from a pre-built user/role/channel map, and preserve unknown message/component types as raw JSON (Components V2 messages hide text/media inside `components`, not `content`).
- **Attachments & packaging — the key upgrade:** download media *into* the export and reference local copies; strip `ex/is/hm` and name files by URL content-hash for dedupe/"reuse media" (DCE's model); refresh signed URLs before they expire. Host permissions should add **`https://media.discordapp.net/*`** (which the analyzed tool lacks).
- **Output & performance:** write chunked, self-contained static HTML (inline CSS, `loading="lazy"`, `content-visibility:auto`), partitioned by count/size, plus a raw `messages.json` for fidelity; stream to disk via `showSaveFilePicker` → `FileSystemWritableFileStream`, zipping with a **ZIP64-capable streaming writer (zip.js or client-zip)** rather than JSZip/conflux. Checkpoint the last message ID and downloaded-asset list in IndexedDB/OPFS so a closed tab can resume.
- **Permissions:** `storage` and `scripting`; add `downloads`/`offscreen` only if actually used; the analyzed tool's `tabs` and `identity` are unnecessary for a purely local free tool.
- **Store compliance:** single-purpose statement, per-permission justifications, a privacy policy declaring "Authentication information" and "Personal communications" as handled-but-not-transmitted, in-UI consent, and **no remote code or obfuscation** ([User Data FAQ](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq)).

## Conclusion

The tool is best understood as a thin, well-marketed wrapper around a non-compliant primitive: it works because it borrows the logged-in user's own credential and talks to Discord's private API as if it were the official client. Everything the user sees — the date picker, the dark transcript, the attachment grid — is downstream of that one decision, and it is also the decision that makes the tool unsafe to depend on, because Discord's 2026 enforcement is actively logging out and penalizing accounts that do exactly this. The engineering itself is unremarkable and cheaply reproducible; the hard parts the market leaders solve (streaming to disk, local media packaging, resumability, honest rate-limit handling) are precisely the parts this extension skips, which is why its exports are fragile (expiring media links, lost progress, a false "success" toast) and why a rebuild can meaningfully beat it with free, open-source pieces and no AI.

The sharper conclusion for this project is a fork in the road. If the goal is a shippable product, the winning move is not a better token-grabber but a **compliant exporter**: a bot-token mode for server owners (self-serve `MESSAGE_CONTENT` is now available under 10,000 users) and clear guidance toward Discord's official "Request your data" package for personal history — the only first-party, ban-proof route, albeit limited to the user's own sent messages. If the goal is purely a local, personal archiving tool for one's own conversations, the architecture above will produce a more durable export than the analyzed extension does, for the price of a cup of coffee — but it should ship with the same blunt warning its predecessors carry, because the capability and the account risk are inseparable.
